# Masonry Row Grid Layout

Column-first masonry, the CSS `columns` kind, reads top to bottom. That is
wrong for a photo grid, because the eye reads left to right and the second
image in the DOM lands halfway down the page. This is the row-first
arrangement instead. The component fills each row to the container's width and
scales it to a height near the target, so neighbouring photographs end up the
same height and both edges of the row stay flush.

## Choosing the rows

The greedy arrangement is the obvious one: keep adding images until the row
overflows, then scale the row down to fit. It is one pass and it is fast, but
it never reconsiders. One tall portrait early on pushes a short row, and the
last row is whatever happens to be left.

The justified arrangement treats it as a shortest-path problem. Every break
point costs the squared distance between the row's height and the target, a
row with a single item costs an extra penalty, and `dp[i]` is the cheapest way
to arrange the first `i` images. Backtracking through `parent[]` gives the
rows. It is O(n²) in the worst case, and the inner loop stops as soon as the
row gets shorter than the minimum, so it only examines the items that could
share one row.

## Measuring, not laying out

`MasonryRowGrid` never reads a DOM node to decide anything. The items carry
their intrinsic width and height, the only measurement is the container's own
width from a `ResizeObserver`, and the component computes every position from
those two numbers. That is why a drag holds its frame rate. Resizing re-runs
the arithmetic instead of reading styles back out of the browser.

The observer's callback coalesces into a `requestAnimationFrame`, so a drag
that fires a hundred resize notifications still produces one layout per frame.

## Using it

The component decides position and size. `renderItem` decides what goes
inside each item container.

```tsx title="page.tsx"
import { MasonryRowGrid } from "@/components/ui/masonry-row-grid";

// Intrinsic dimensions, not display ones. Only the ratio matters.
const items = [
  { width: 2500, height: 1667, src: "/photos/01.jpg" },
  { width: 2448, height: 3264, src: "/photos/02.jpg" },
  // ...
];

export default function Page() {
  return (
    <MasonryRowGrid
      items={items}
      targetHeight={270}
      layout="justified"
      renderItem={(item, index, measures) => (
        <img
          src={item.src as string}
          alt={`Photograph ${index + 1}`}
          width={measures.width}
          height={measures.height}
          className="size-full rounded-md object-cover"
        />
      )}
    />
  );
}
```

## Layout modes

<Callout type="tip" title="Which mode">
  Use `justified` for a finite set, where the component solves the whole
  arrangement once and can balance the rows against each other. Use `naive`
  for infinite scroll or anything that loads in, where a later item must not
  move an earlier row.
</Callout>

`naive` fills each row until it overflows the container, then scales that row
down to fit. It never revisits a row, so a row is final once it closes, and
appending items cannot move what is already on screen. The cost is the last
row, which holds whatever was left over and is often short.

`justified` solves all the rows together, so every row is flush and heights
stay near the target. Adding an item re-solves the whole arrangement, so rows
that were already placed can shift.

## Structure

The component positions every item absolutely inside one relative container,
so the container needs the computed total height. The gap is padding inside
each item rather than a margin between items, which keeps the row arithmetic
in whole container widths.

```text noLineNumbers
Root container (div)
 │  └─ position: relative; height: <totalHeight>px
 │
 ├─ Item container (div)
 │   │  └─ position: absolute; top/left/width/height from measures;
 │   │     padding: <gap>px, halved on any edge shared with a neighbour
 │   └─ renderItem(item, index, measures)
 │
 ├─ Item container (div)
 │   └─ ...
 └─ ...
```
