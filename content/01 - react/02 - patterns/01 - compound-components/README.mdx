# Compound components

Instead of one component with twenty configuration props, expose a small family of subcomponents that coordinate through context.

## The problem with prop explosion

A configurable accordion grows props like `headerClassName`, `renderIcon`, `iconPosition` and `hideDivider`. Each one guesses at a caller's layout, and none of them compose.

## The pattern

```tsx
<Accordion defaultOpen="billing">
  <Accordion.Item value="billing">
    <Accordion.Trigger>Billing</Accordion.Trigger>
    <Accordion.Panel>Invoices and payment methods.</Accordion.Panel>
  </Accordion.Item>
  <Accordion.Item value="security">
    <Accordion.Trigger>Security</Accordion.Trigger>
    <Accordion.Panel>Sessions and two-factor settings.</Accordion.Panel>
  </Accordion.Item>
</Accordion>
```

The parent owns the open state, and each subcomponent reads it from a private context.

## Guarding the context

Throw when a subcomponent renders outside its parent:

```typescript
const AccordionContext = createContext<AccordionState | null>(null);

function useAccordionContext(component: string) {
  const context = useContext(AccordionContext);
  if (!context) {
    throw new Error(`<${component}> must be rendered inside <Accordion>.`);
  }
  return context;
}
```

An error during development costs one stack trace. A component that renders nothing costs an afternoon.

## Trade-offs

- A caller can reorder and wrap the parts, which is the point of the pattern.
- A caller can also build an invalid structure, so the context guard is not optional.
- Static properties on the parent defeat tree-shaking. Export each subcomponent on its own as well.
