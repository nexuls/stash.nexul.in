# useLocalStorage hook

Keeps a piece of React state in `localStorage` so it survives a reload, and stays safe to render on the server.

## Overview

Reading `window.localStorage` during the first render breaks server rendering and causes a hydration mismatch. This version reads in an effect instead, and keeps a lazy initializer for the client-only case.

## Implementation

The implementation sits beside this guide in [`use-local-storage.ts`](./use-local-storage.ts):

```typescript
import { useCallback, useEffect, useState } from "react";

export function useLocalStorage<T>(key: string, initialValue: T) {
  const [value, setValue] = useState<T>(initialValue);

  useEffect(() => {
    try {
      const raw = window.localStorage.getItem(key);
      if (raw !== null) {
        setValue(JSON.parse(raw) as T);
      }
    } catch {
      // Ignore unavailable or corrupt storage
    }
  }, [key]);

  const write = useCallback(
    (next: T) => {
      setValue(next);
      try {
        window.localStorage.setItem(key, JSON.stringify(next));
      } catch {
        // Quota exceeded or private mode
      }
    },
    [key],
  );

  return [value, write] as const;
}
```

## Cross-tab synchronization

The `storage` event fires in every other tab of the same origin, which makes it a cheap synchronization channel:

```typescript
useEffect(() => {
  function onStorage(event: StorageEvent) {
    if (event.key === key && event.newValue !== null) {
      setValue(JSON.parse(event.newValue) as T);
    }
  }

  window.addEventListener("storage", onStorage);
  return () => window.removeEventListener("storage", onStorage);
}, [key]);
```

## Caveats

- A value must be JSON-serializable. `Date` and `Map` need a custom reviver.
- A write is synchronous and blocks the main thread, so keep payloads small.
- A private browsing window may throw on a write even when reads succeed.
