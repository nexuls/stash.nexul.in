# Reducer store

An application reaching for a state library usually needs a typed reducer, a stable dispatch, and subscriptions that do not re-render every consumer. React already has all three.

## Typed reducer

```typescript
type Action =
  | { type: "filter/set"; value: string }
  | { type: "selection/toggle"; id: string }
  | { type: "selection/clear" };

interface State {
  filter: string;
  selected: Set<string>;
}

export function reduce(state: State, action: Action): State {
  switch (action.type) {
    case "filter/set":
      return { ...state, filter: action.value };
    case "selection/toggle": {
      const selected = new Set(state.selected);
      if (!selected.delete(action.id)) {
        selected.add(action.id);
      }
      return { ...state, selected };
    }
    case "selection/clear":
      return { ...state, selected: new Set() };
  }
}
```

An exhaustive `switch` over a discriminated union makes a new action type a type error until something handles it.

## Splitting the context

Put state and dispatch in separate contexts. A component that only dispatches then never re-renders when the state changes:

```tsx
<StateContext.Provider value={state}>
  <DispatchContext.Provider value={dispatch}>{children}</DispatchContext.Provider>
</StateContext.Provider>
```

`dispatch` keeps the same reference across renders, so its context never invalidates.

## Selector subscriptions

Context hands the whole value to every consumer. When that becomes the bottleneck, move the state into an external store and subscribe through selectors:

```typescript
const filter = useSyncExternalStore(
  store.subscribe,
  () => store.getSnapshot().filter,
  () => initialState.filter,
);
```

The third argument is the server snapshot. Leave it out and hydration breaks.

## When to reach for a library

Adopt one when you need middleware, devtools time-travel or cross-tab persistence without writing it. Do not adopt one to avoid writing a reducer.
